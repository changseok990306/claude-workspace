# PRD — 어도비 캠페인 히스토리 (`/history`)

작성일 2026-11-08 · 상태: v2 (포트폴리오와 같은 배포 방식으로 재설계)

## 1. 배경과 목표
어도비 계정을 운영하다 보면 캠페인마다 변경·이슈·결정 이력이 많이 쌓인다. 이를 **캠페인 단위로 날짜와 함께 기록**하고, **키워드나 날짜로 즉시 찾을 수 있는** 개인용 웹페이지를 만든다.

- 성공 기준: 캠페인을 고르고 → 날짜와 내용을 적고 → 추가 버튼 한 번으로 저장되며, 새로고침해도 남아 있고, 검색창에 한 글자만 쳐도 목록이 바로 걸러진다.

## 2. 사용자와 사용 환경
- 사용자: 본인 1명(마케터). 주로 PC 웹 브라우저. 모바일은 깨지지 않을 정도.
- 접근: 로그인 없음(공개). 포트폴리오 주소 뒤 `/history`로 접속.

## 3. 범위
| 포함 | 제외(이번엔 안 함) |
|---|---|
| 캠페인 추가·이름/색상 수정·삭제 | 히스토리 **내용 수정**(지우고 다시 작성) |
| 히스토리 추가·삭제, 날짜 입력 | 파일/이미지 첨부 |
| 날짜 최신순 타임라인 | 로그인·권한 구분 |
| 실시간 검색(내용+날짜) | 내보내기/가져오기 |
| 다크/라이트 전환, 반응형 | 알림, 통계 차트 |

## 4. 기능 요구사항
| # | 요구사항 | 상세 |
|---|---|---|
| F1 | 캠페인 관리 | 이름(1~40자)·색상 8종 중 선택. 삭제 시 확인창, 소속 히스토리도 함께 삭제. 사이드바(≥1024px) / 상단 칩(그 미만)으로 전환, "전체" 보기 제공 |
| F2 | 히스토리 입력창 | 캠페인 선택 + 날짜(기본 오늘) + 내용(1~1000자). `Ctrl+Enter`로 추가 |
| F3 | 히스토리 추가/삭제 | 항목마다 삭제 버튼, 삭제 전 확인 |
| F4 | 날짜 입력 | `<input type="date">`. 존재하지 않는 날짜(2026-02-30)는 서버가 거절 |
| F5 | 새로고침 유지 | 모든 데이터는 Supabase DB에 저장. 마지막에 본 캠페인·테마는 브라우저에 기억 |
| F6 | 다크/라이트 토글 | 우측 상단 스위치. 다크: 배경 `#1A1A1A` / 카드 `#2D2D2D` / 텍스트 `#E0E0E0`. 전환 0.3초. 첫 방문은 OS 설정을 따름 |
| F7 | 실시간 검색 | 입력할 때마다 필터. 내용·날짜·캠페인명 대상. 날짜는 `2026-11`, `11월 8일` 등 여러 표기 허용. 단어가 여러 개면 모두 포함된 글만. 일치 단어 하이라이트, 결과 개수 표시 |
| F8 | 정렬 | 히스토리 날짜 **최신순(위) → 오래될수록 아래**. 같은 날짜는 나중에 쓴 글이 위. 날짜별 그룹 제목 |
| F9 | 반응형 | ≥1024px 2단(사이드바+본문), 그 미만 1단. 375px에서도 가로 스크롤 없음 |
| F10 | 캠페인 색 구분 | 사이드바 점, 카드 왼쪽 띠, 배지, 입력창 상단 선, 제목 띠에 캠페인 색 적용 |

> 요구사항 원문의 마지막 문장("최신순으로 오래될수록 정…")이 중간에 끊겨 있어 F8처럼 해석했다. 의도와 다르면 알려 주세요.

## 5. 디자인
- **참조 테마: WordPress Twenty Twenty-Four** — 절제된 타이포, 넉넉한 여백, 카드형 블록이 "기록/아카이브형 도구"와 가장 잘 맞는다고 판단(필자의 선택이며 테마 코드를 가져오지 않고 분위기만 참고).
- 라이트: 배경 `#F7F6F2`, 카드 흰색. 다크: 위 지정색.
- **캠페인 8색**: 인디고·청록·호박·장미·초록·보라·주황·회색. 라이트에서는 진한 색, 다크에서는 밝은 색으로 바꿔 글자 대비 4.5:1 이상을 유지.
- 접근성: 토글은 `role="switch"`, 포커스 표시, `prefers-reduced-motion`이면 애니메이션 끔.

## 6. 기술 방향
```
브라우저(/history)  →  Vercel 서버 함수(/api/campaigns, /api/histories)  →  Supabase(DB)
```
| 결정 | 이유 |
|---|---|
| 프레임워크 없는 정적 HTML/CSS/JS | 포트폴리오와 동일. 빌드 단계가 없어 배포가 가장 단순 |
| 기존 Vercel 프로젝트에 `portfolio/history/`로 추가 | 새 프로젝트·새 환경변수가 필요 없음. 포트폴리오에서 이미 된 설정을 그대로 사용 |
| 서버 함수 경유 | 입력 검증(길이·날짜 형식·id 형식)과 쓰기 횟수 제한을 한곳에서 처리 |
| 환경변수 `SUPABASE_URL`, `SUPABASE_ANON_KEY` | 포트폴리오 방명록과 동일(이미 Vercel에 등록됨) |
| 사용자 입력은 `textContent`로만 출력 | `<script>` 등이 실행되지 않게(XSS 방지) |

### 데이터 모델 (`supabase/history.sql`)
- `campaigns(id uuid, name text 1~40, color text(8종), created_at)`
- `histories(id bigint, campaign_id → campaigns **on delete cascade**, content text 1~1000, event_date date, created_at)`
- 인덱스: `histories(event_date desc, created_at desc)`, `histories(campaign_id)`
- RLS 켬. 공개 키(anon)에 허용: 두 테이블 읽기·추가·삭제, 캠페인 수정. 컬럼 단위로 입력 가능한 칸을 제한.

### API
| 경로 | 메서드 | 설명 |
|---|---|---|
| `/api/campaigns` | GET / POST / PATCH(?id) / DELETE(?id) | 캠페인 목록·추가·수정·삭제 |
| `/api/histories` | GET(?campaign_id) / POST / DELETE(?id) | 히스토리 목록·추가·삭제 |
| 공통 | | 같은 IP가 1분에 60번 넘게 추가·삭제하면 429 |

## 7. 보안과 위험 (솔직한 한계)
- **로그인이 없다.** 주소를 아는 사람은 누구나 기록을 보고, 추가하고, 지울 수 있다. (사용자가 "완전 공개"를 선택)
- 공개 키로 DB에 직접 접근할 수 있는 구조라, 서버 함수의 쓰기 제한은 **우회될 수 있다.** 포트폴리오 방명록과 같은 수준의 공개 방식이지만 이번에는 삭제도 가능하다.
- 업무 내용(고객명, 금액 등 민감 정보)은 적지 않는 것을 권장한다.
- Supabase 무료 플랜은 자동 백업이 보장되지 않는다. 중요한 기록은 따로 복사해 둔다.
- 검색엔진에 잡히지 않도록 `noindex`를 설정하고, 포트폴리오에서 링크는 걸지 않는다.
- 나중에 잠그고 싶으면: 로그인(Supabase Auth)을 붙이는 별도 작업이 필요하다.

## 8. 수용 기준 (검사로 확인)
1. 추가 → 새로고침 → 그대로 남아 있다.
2. 날짜 최신순으로 위에서 아래로 나열된다.
3. 검색: 내용(`배너`), 날짜(`2026-11`, `11월 8일`), 여러 단어(`배너 테스트`)가 모두 즉시 걸러진다.
4. 다크 전환 시 배경/카드/텍스트가 정확히 `#1A1A1A` / `#2D2D2D` / `#E0E0E0`, 전환 시간 0.3초.
5. 캠페인 삭제 시 소속 히스토리도 함께 삭제된다.
6. `<script>…</script>`를 입력해도 글자 그대로 표시된다.
7. 375px / 768px / 1280px에서 가로 스크롤이 없다.
8. 기존 포트폴리오(`/`)와 방명록 API는 그대로 동작한다.

## 9. 배포 순서 (사용자)
1. Supabase SQL Editor에 `supabase/history.sql`을 붙여넣고 Run.
2. 코드를 main에 push하면 기존 Vercel 프로젝트가 **자동으로 다시 배포**한다. (환경변수는 이미 있으므로 추가 없음)
3. `포트폴리오주소/history` 접속.
